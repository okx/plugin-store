## Step 1 — UX exploration (G1: MANDATORY)

**Skill:** `explore-plugin`
**Invocation:** `Skill(skill="explore-plugin", args="across-protocol-onchainos")`
**Live funds needed:** ❌ no

The explore-plugin skill simulates a brand-new user. It will:
- Read SKILL.md cold and note anything confusing
- Run every read-only tool (`listSupportedChains`, `getQuote`, `getDepositStatus`) and question every output
- Probe edge cases (zero amount, malformed token addresses, wrong chain IDs) against validators
- Drive `buildSwap` to its `pending_sign` stage and verify the approve-then-action flow makes sense

**Pass criterion (G1):** Zero Major+ findings — OR — every Major+ finding patched in the same pass and re-explored.

## Step 5 — Live on-chain test (G3: OPTIONAL)

### G3 live-test matrix

| Tool | Class | Pre-state needed | Live cost | Reversibility | G3 recommendation |
|------|-------|------------------|-----------|---------------|-------------------|
| `listSupportedChains` | Read | none | none | n/a | N/A — covered by Step 3 (B-real) |
| `getQuote` | Read | none | none | n/a | N/A — covered by Step 3 (B-real) |
| `getDepositStatus` | Read | a prior deposit tx hash | none | n/a | N/A — covered by Step 3 once a real deposit exists |
| `buildSwap` (approve step) | Tx-approve | none | gas only (~$1 on Arbitrum / Base, can spike on Ethereum mainnet) | revoke via separate `erc20.approve(spender, 0)` | ✅ cheap-validate; also confirms multi-step state machine emits Step 2 on re-invocation |
| `buildSwap` (bridge step) | Tx-multi-step | approve from Step 1 + input-token balance ≥ amount on origin chain | gas (~$1) + value (the bridged amount, e.g. 5 USDC) | soft — destination fill typically lands in <2s on mainnet; reversible by bridging back | ⚠️ commit-funds; smallest sensible test is 5 USDC Arbitrum → Base (~$5 + gas) |

### Default G3 scope

Test every ✅ row, ask the user before any ⚠️ row. For Across specifically: the bridge step is mostly reversible (fill lands fast, can bridge back), so the ⚠️ commit-funds risk is short-lived — still requires explicit user opt-in per the standard rule.

### Live broadcast pattern

```bash
onchainos wallet contract-call \
  --chain <chain> \
  --to <unsigned_tx.to> \
  --input-data <unsigned_tx.data> \
  --amt <unsigned_tx.value> \
  --biz-type defi \
  --strategy across-protocol-onchainos \
  --force
```

For the multi-step flow:

1. Call `buildSwap` → first `pending_sign` (approve, with `step_info: {current:1, total:2}`)
2. Broadcast via `onchainos wallet contract-call`
3. Wait for the receipt
4. Re-call `buildSwap` with the same params → tool re-reads allowance, emits Step 2 (the swap tx)
5. Broadcast Step 2 via `onchainos wallet contract-call`
6. (Optional) Poll `getDepositStatus({depositTxnRef: <txHash>, originChainId})` until the destination fill confirms

## When all 5 steps pass

The plugin is production-ready. Record any live tx hashes from Step 5 in the Migration note of SKILL.md for audit traceability.
