## Migration / scope note (generated by dapp-connect-agenticwallet)

This skill is the OnchainOS-routed evolution of upstream [`lista-dao/lista-skills`](https://github.com/lista-dao/lista-skills). All on-chain signing flows through the tools in `requiredTools` (`onchainos wallet contract-call`, `onchainos gateway broadcast`); the `requires: lista-wallet-connect` frontmatter field is preserved for historical traceability but is **not** load-bearing at runtime. Read-only commands (`listVaults`, `listMarkets`, `getHoldings`) are pass-through and do not invoke Onchain OS.

### Tool surface (12 tools)

**Transaction tools** (return `pending_sign | ToolError`):
- `buildDeposit`, `buildWithdraw` — vault ops (ERC-4626 vaults)
- `buildSupply`, `buildBorrow`, `buildRepay`, `buildMarketWithdraw` — market ops (Moolah lending)

**Read-only tools** (return `{status: 'ok', ...} | ToolError`):
- `listVaults`, `listMarkets`, `getHoldings`, `getVaultPosition`, `simulateBorrow`, `simulateRepay`

### Scaffold patterns applied (v1.14)

- `validateDecimals` (P1-15) — enforced on every `parseUnits` boundary
- `nativeBalanceCheck` (P1-14) — wired on every transaction tool (no-op for `value=0` ERC-20 ops)
- `lc()` (P1-10) — applied to every EVM address at viem/SDK boundaries
- `PUBLIC_RPCS` (P2-15) — pinned to publicnode; override via `LISTA_RPC_*` env
- `safeSdkCall` — wraps every `listaSdk.*` and `erc20.*` call so transient SDK / RPC / viem failures surface as structured `ToolError` (`UNKNOWN_VAULT` / `UNKNOWN_MARKET` / `RPC_ERROR` / `SDK_ERROR`) instead of escaping as uncaught throws
- Mandatory G1 (`explore-plugin`) + G2 (`test-skill`) gates per the scaffold's Step 6.5

### Error code catalog

| Error code | Failure mode |
|---|---|
| `UNKNOWN_VAULT` | Vault address doesn't resolve (not a contract, paused, or wrong chain) |
| `UNKNOWN_MARKET` | Market ID doesn't resolve on the target chain |
| `RPC_ERROR` | RPC failure reading user data or ERC-20 allowance |
| `SDK_ERROR` | Moolah SDK failed to assemble calldata |
| `INVALID_MARKET` | Market resolves but has no loan asset configured |
| `NO_VAULT_POSITION` | User has no shares in the requested vault |
| `EXCEEDS_BALANCE` / `EXCEEDS_DEBT` / `EXCEEDS_WITHDRAWABLE` | Requested amount exceeds the relevant cap |
| `INSUFFICIENT_BORROW_CAPACITY` | Borrow would exceed loanable headroom |
| `EXCEEDS_SAFE_BORROW_CAP` | Borrow would exceed 95% of loanable (liquidation risk) |
| `WITHDRAW_ALL_HAS_DEBT` | `withdrawAll` blocked because outstanding debt remains |
| `NO_COLLATERAL` / `NO_DEBT_TO_REPAY` | No position to act on |

## Proactive Onboarding

When a user signals they are **new or just installed** this skill — e.g. "I just installed lista-lending-onchainos", "how do I get started with Lista", "what can I do with this" — **do not wait for them to ask specific questions.** Walk them through the Quickstart in order, one step at a time, waiting for confirmation before proceeding:

1. **Check wallet** — run `onchainos wallet addresses --chain bsc` (or `--chain ethereum`). If no address, direct them to `onchainos wallet login`. Do not proceed until a wallet is confirmed.
2. **Check balance** — run `onchainos wallet balance --chain bsc`. If insufficient, explain what's needed (BNB for gas + collateral token to deposit/supply).
3. **Browse what's available** — call `listVaults({chain: 'bsc'})` or `listMarkets({chain: 'bsc'})` to show available targets. Ask whether the user wants to lend (vault) or borrow against collateral (market).
4. **Simulate first** — for borrow/repay flows, call `simulateBorrow` / `simulateRepay` first to surface capacity / health impact before any tx.
5. **First write** — call the relevant `build*` tool. If the response is `pending_sign`, route to `onchainos wallet contract-call` per `next_action.tool`. If the response is `{status:'error'}`, explain the error to the user.
6. **Multi-step alert** — if the response description says "Step 1 of 2: Approve ...", explain that the user will sign the approval, then you'll re-invoke the same `build*` tool to get the action transaction.

Do not dump all steps at once. Guide conversationally — confirm each step before moving on.

## Quickstart

New to `lista-lending-onchainos`? Follow these steps to go from zero to your first supply/borrow on Lista.

### Step 1 — Confirm onchainos is ready

The Initialization block at the top of this skill runs automatically. After it completes, confirm:

```bash
onchainos --version
onchainos wallet status
```

If `wallet status` shows `loggedIn: false`, run `onchainos wallet login your@email.com` and complete the OTP flow.

### Step 2 — Check wallet balance

```bash
onchainos wallet balance --chain bsc
```

Minimum recommended: ~$1 in BNB for gas + a small amount of the asset you want to supply/deposit (USDT, USD1, BTCB, etc.). If zero, bridge or transfer from a CEX to your wallet's BSC address.

### Step 3 — Browse what's available

```javascript
// Option A — lend (passive yield via a vault)
listVaults({ chain: 'bsc', sort: 'apy', order: 'desc', pageSize: 10 })

// Option B — supply collateral + borrow against it (market)
listMarkets({ chain: 'bsc', sort: 'liquidity', order: 'desc', pageSize: 10 })
```

Note the `address` (vault) or `marketId` of one that looks interesting — you'll need it for the next step.

### Step 4 — Simulate before borrowing (optional but recommended)

```javascript
simulateBorrow({
  marketId: '0x<marketId>',
  walletAddress: '0x<your-address>',
  chain: 'bsc',
})
```

Returns projected loanable capacity and the 95%-safe borrow cap. Use this to size your borrow correctly.

### Step 5 — Build a transaction (preview)

```javascript
// Vault deposit
buildDeposit({
  vaultAddress: '0x<vault>',
  amount: '0.1',         // UI-units, NOT wei
  walletAddress: '0x<your-address>',
  chain: 'bsc',
})

// Market collateral supply
buildSupply({
  marketId: '0x<marketId>',
  amount: '0.1',
  walletAddress: '0x<your-address>',
  chain: 'bsc',
})
```

You'll receive ONE of:
- `{status: 'pending_sign', unsigned_tx: {to, data, value, chain}, description, next_action: {tool: 'onchainos wallet contract-call'}}` — proceed to Step 6
- `{status: 'error', error_code: '...', message: '...', suggestion?: '...'}` — fix the input and retry

### Step 6 — Sign + broadcast via onchainos

```bash
onchainos wallet contract-call \
  --chain bsc \
  --to <unsigned_tx.to> \
  --input-data <unsigned_tx.data> \
  --amt <unsigned_tx.value> \
  --biz-type defi \
  --strategy lista-lending-onchainos \
  --force
```

> Flag-name notes (verified live 2026-05-11):
> - `--input-data` (not `--data`) — the EVM calldata hex
> - `--amt` (not `--value`) — native token amount in wei, default 0
> - `--biz-type` + `--strategy` populate transaction metadata (helpful for audit)
> - `--force` skips backend confirmation prompts (use only when the user has already confirmed via the agent flow)

Wait for the broadcast confirmation.

### Step 7 — Multi-step: re-invoke if you got an approve step

If the description from Step 5 started with `"Step 1 of 2: Approve ..."`, the transaction was an ERC-20 approve. Once it lands, re-invoke the **same `build*` tool with the same params** — this time it will return the actual deposit/supply/repay step.

### Step 8 — Verify

For vault deposits, use `getVaultPosition` for immediate real-time confirmation (bypasses the Lista API indexer lag of ~30–60s):

```javascript
getVaultPosition({
  vaultAddress: '0x<vault>',
  walletAddress: '0x<your-address>',
  chain: 'bsc',
})
```

For a broader portfolio view (vault + market positions, with isSmartLending / isFixedTerm / health flags), use `getHoldings` — but allow up to a minute for fresh positions to appear:

```javascript
getHoldings({ address: '0x<your-address>', chain: 'bsc', scope: 'all' })
```

## Error Code Catalog

Every `build*` tool returns either `pending_sign` (success) or a `ToolError` shape. Possible error codes:

| Code | Meaning | What to suggest |
|---|---|---|
| `UNSUPPORTED_CHAIN` | `params.chain` is not 'bsc' or 'ethereum' | Use one of the supported chains |
| `MISSING_PARAM` | A required field is missing | Provide the named field |
| `INVALID_PARAM` | A field has an invalid value (non-decimal amount, both amount+repayAll set, etc.) | Fix per the error message |
| `INVALID_MARKET` | Market ID doesn't resolve to a valid Lista market | Use `listMarkets` to find a valid ID |
| `MISSING_AMOUNT` | Neither `amount` nor `repayAll`/`withdrawAll` was provided | Provide one |
| `INSUFFICIENT_BORROW_CAPACITY` | Requested borrow > loanable | Use `simulateBorrow` to size correctly; supply more collateral first |
| `EXCEEDS_SAFE_BORROW_CAP` | Requested borrow > 95% of loanable | Stay at or below 95% of loanable |
| `EXCEEDS_DEBT` | Requested repay > current debt | Use amount up to current debt, or `repayAll: true` |
| `EXCEEDS_BALANCE` | Requested vault withdraw > vault balance | Use amount up to balance, or `withdrawAll: true` |
| `EXCEEDS_WITHDRAWABLE` | Requested collateral withdraw > LLTV-safe cap | Withdraw less, or repay debt first |
| `NO_DEBT_TO_REPAY` | Market has zero debt | Nothing to repay |
| `NO_VAULT_POSITION` | User has zero shares in the vault | Nothing to withdraw |
| `NO_COLLATERAL` | User has zero collateral supplied to the market | Nothing to withdraw |
| `WITHDRAW_ALL_HAS_DEBT` | Tried withdrawAll with outstanding debt | Repay all debt first (`buildRepay { repayAll: true }`) |
| `MISSING_ADDRESS` | `getHoldings` requires `address` param | Provide the wallet address |
| `NO_POSITION` | `getVaultPosition` found zero shares | User hasn't deposited to this vault (or has already withdrawn) |

## Temporary Limitations

Current unsupported market types for trade actions (`select/supply/borrow/repay/market-withdraw`):

- SmartLending markets (`zone === 3`)
- Fixed-term markets (`termType === 1`)

Behavior:

- `markets` command filters them out from list output.
- `select --market` rejects them with `unsupported_market_type`.
- `holdings` still returns them (for full portfolio visibility) and marks:
  - `isSmartLending`
  - `isFixedTerm`
  - `isActionable`

## Command Index

> **Note:** The upstream CLI names below (`deposit`, `borrow`, etc.) map to the typed
> tool functions in `index.ts` (`buildDeposit`, `buildBorrow`, etc.). Invoke the typed

- `simulateRepay` — dry-run repay impact check (debt after, health after)

- `version`, `config`, `select` — replaced by onchainos equivalents or by stateless per-call params

## Transaction Behavior

- Transactions are built by SDK and executed through `lista-wallet-connect` `call` command.
- `call` performs simulation by default before requesting wallet signature.
- If simulation fails, result is returned as error/reverted and no signing request is sent.
- If user rejects in wallet, command returns `status: "rejected", reason: "user_rejected"`.
- For multi-step operations (approve + action), responses include completed step count and failed/pending step.

## Typical Workflows

### Vault flow

```bash
# 1) discover
node dist/cli/cli.bundle.mjs vaults --chain eip155:56

# 2) select
node dist/cli/cli.bundle.mjs select --vault 0xVAULT --wallet-topic <topic> --wallet-address 0xADDR

# 3) operate
node dist/cli/cli.bundle.mjs deposit --amount 1
node dist/cli/cli.bundle.mjs withdraw --amount 0.5
```

### Market flow

```bash
# 1) discover
node dist/cli/cli.bundle.mjs markets --chain eip155:56

# 2) select
node dist/cli/cli.bundle.mjs select --market 0xMARKET --wallet-topic <topic> --wallet-address 0xADDR

# 3) operate
node dist/cli/cli.bundle.mjs supply --amount 2
node dist/cli/cli.bundle.mjs borrow --simulate
node dist/cli/cli.bundle.mjs borrow --amount 0.01
node dist/cli/cli.bundle.mjs repay --simulate --amount 0.01
node dist/cli/cli.bundle.mjs repay --amount 0.01
node dist/cli/cli.bundle.mjs market-withdraw --amount 1
```

## Security Checklist

1. Confirm token symbol and amount with user before any state-changing action.
2. Confirm chain (`eip155:56` vs `eip155:1`) before sending tx.
3. Prefer `borrow --simulate` before first borrow on a market.
4. Treat `user_rejected` as normal user decision, not protocol failure.
